# 1.2.0 release checklist — rewarded ads / AI credits

Internal notes only. Not read by `.github/workflows/android-release.yml` (it only
reads `changelogs/<version>.en.txt` and `changelogs/<version>.fa.txt` as store
release notes) and not bundled into the app — this file exists purely so the
store-console steps, credential swaps, deploy ordering, and pre-migration
checks below aren't forgotten before this version ships.

It is the companion to the "Launch checklist" section of
`docs/superpowers/plans/2026-08-01-ads-for-ai-credits.md`; that one covers the
server-side rollout order, this one covers everything store- and build-side.
It has since grown to also cover the Cafe Bazaar billing, Tapsell rewarded-ad,
and Play Protect items added by
`docs/superpowers/plans/2026-08-01-bazaar-billing-and-tapsell-ads.md`.

## CRITICAL: apply `20260802000000_pass_verification.sql` before deploying `ai-proxy`

`ai-proxy` checks premium via `admin.rpc("tally_has_active_entitlement")`. If
that migration hasn't been applied yet, the function does not exist, the RPC
call errors, `ai-proxy` fails closed (`isPremium = false` — correct, safe
behavior in isolation), and **every** entitled user — staff/alpha comp,
legacy Apple subscribers, and every verified Bazaar pass holder — silently
stops being recognized as premium. They start being billed AI credits like a
free user until their balance runs out, then get 402'd, with nothing in the
UI explaining why (they still see an active pass / alpha flag).

Nothing sequences this automatically — not the `Makefile`, not CI. Deploy
order is entirely on the operator:

- [ ] Apply `supabase/migrations/20260802000000_pass_verification.sql` (see
      "Before applying the migration to production" below for the by-hand
      dashboard process) **before** running `make ai-proxy-deploy` /
      `supabase functions deploy ai-proxy`, every time either could be out of
      sync — first deploy and any redeploy alike.

## Play Protect (1.1.0 → 1.2.0 rejection)

Bazaar rejected versionCode 8 with "Play Protect hasn't seen an app from this
developer before." This is signing reputation, not a code defect.

- [ ] Confirm `ANDROID_KEYSTORE_BASE64` is byte-identical to the keystore that
      signed the accepted 1.1.0 build. A rotated key resets reputation and is
      the most likely cause. Compare the certificate fingerprint:
      `keytool -list -v -keystore keystore.jks | grep SHA256`
- [ ] File Google's Play Protect appeal at
      https://support.google.com/googleplay/android-developer/contact/appeal-protect
      Allow up to 3 days — Bazaar's own guidance notes the warning can persist
      that long after a fix.
- [ ] Re-verify after this release: it adds two ad SDKs, which Bazaar lists as
      a contributing factor. If the warning worsens, test a build with
      `EXPO_PUBLIC_AD_NETWORK` unset to isolate which SDK is implicated.

## Cafe Bazaar billing

Steps below are ordered so each one can actually succeed given the ones
before it — migration first (later steps depend on `verified_at` existing),
then secrets, then the function that needs them, then device verification.

- [ ] Apply `supabase/migrations/20260802000000_pass_verification.sql` (adds
      `pass_entitlements.verified_at` and `tally_has_active_entitlement`) —
      see "Before applying the migration to production" below. Also see the
      CRITICAL section above the top of this file: this migration must be
      live before `ai-proxy` is (re)deployed.
- [ ] Set the **six** server secrets: `make verify-bazaar-purchase-secrets`
      (not `verify-bazaar-secrets` — that target doesn't exist). The six are
      `BAZAAR_CLIENT_ID`, `BAZAAR_CLIENT_SECRET`, `BAZAAR_REFRESH_TOKEN`,
      `BAZAAR_PACKAGE_NAME`, `BAZAAR_PASS_PRODUCT_MAP`, and
      `BAZAAR_EXTEND_PRODUCT_MAP` — missing `BAZAAR_PASS_PRODUCT_MAP` is easy
      to do by habit and makes `verify-bazaar-purchase` return
      `500 server_misconfigured` for every single purchase attempt.
- [ ] Confirm `BAZAAR_EXTEND_PRODUCT_MAP` lists the three `.extend` SKUs and
      that **no SKU appears in both maps** — an overlap is refused at request
      time with `500 server_misconfigured`, because whichever map won would
      decide whether the user's money buys a full pass or an extension.
      Leaving this secret unset is a valid choice: extensions stay off and
      `.extend` SKUs answer `400 unknown_product`, exactly as in 1.2.0.
      Buying is unaffected either way.
- [ ] Set `EXPO_PUBLIC_BAZAAR_RSA_PUBLIC_KEY` (Pishkhan → app → in-app billing)
      as an EAS environment variable — this is the switch
      `isBazaarBillingAvailable()` checks to turn on Bazaar billing at all;
      without it every purchase attempt on a Bazaar build silently falls
      through to `unavailable`.
- [ ] Set the three pass SKUs (`EXPO_PUBLIC_NIGHT_OUT_PASS_ID`, `_TRIP_PASS_ID`,
      `_EXPLORER_PASS_ID`) as EAS environment variables. **Without these the
      Plans screen offers passes that cannot be bought** — the inverse of the
      1.1.0 bug, where they were granted free. The symptom is the alert
      "خرید در این نسخه در دسترس نیست" (`premium.errorNotConfigured`), raised
      by `buyOrStub` in `PremiumContext.tsx` the moment it is handed a null SKU.
- [ ] Set the three extend SKUs (`EXPO_PUBLIC_NIGHT_OUT_EXTEND_ID`,
      `_TRIP_EXTEND_ID`, `_EXPLORER_EXTEND_ID`) as EAS environment variables,
      and make sure they match `BAZAAR_EXTEND_PRODUCT_MAP` exactly. Skipping
      these is safe — the expired-pass prompt just can't offer the cheaper
      renewal — but a MISMATCH is not: the client would charge for a SKU the
      server answers `400 unknown_product` for, and the user pays with nothing
      granted.
- [ ] Set `EXPO_PUBLIC_AD_NETWORK=tapsell` and
      `EXPO_PUBLIC_TAPSELL_REWARDED_ZONE_ID` (from the Tapsell publisher
      panel) as EAS environment variables for the Bazaar build variant.
      Without these the build falls back to AdMob, which Bazaar/Myket
      installs don't have Google Play services for — rewarded ads silently
      never fill.
- [ ] Deploy the function: `make verify-bazaar-purchase-deploy` (or
      `make verify-bazaar-purchase` to also (re)push the six secrets above).
- [ ] Buy each of the three passes on a real device from a Bazaar install and
      confirm a `pass_entitlements` row appears with `verified_at` set.
- [ ] Confirm a hand-inserted row with `verified_at = null` does NOT unlock AI.

## Ad credits

- [ ] Apply both migrations, then run `supabase/scripts/test_ai_credits.sql` and
      `supabase/scripts/test_pass_verification.sql` against a scratch database.
      Never against production — both insert into `auth.users`.
- [ ] Set `AD_REWARD_DAILY_CAP` (default 30). Confirm the 429 `daily_cap_reached`
      path by claiming past the cap.
- [ ] Confirm `/ad-reward/nonce` rejects `provider: "admob"` with 400.
- [ ] Run a real `assembleRelease` (or equivalent Gradle build — no environment
      up to and including this fix round has had the Android SDK to do this)
      and inspect the **merged** `android/app/build/intermediates/merged_manifest/.../AndroidManifest.xml`
      for the `com.google.android.gms.ads.APPLICATION_ID` meta-data. Confirm it
      resolves to the real AdMob app id, not an empty string. Why this matters:
      Tapsell's own library manifest (`AndroidManifestNew.xml`, inside
      `@react-native-tapsell-mediation/tapsell`) declares the *same* meta-data
      key, sourced from `TapsellMediationAdmobAdapterSignature` in `app.json`'s
      `react-native-tapsell-mediation` block — which this plan never sets, so it
      resolves to `""` (confirmed by reading the library's `android/build.gradle`
      manifest-placeholder wiring). `react-native-google-mobile-ads`'s config
      plugin writes this app's real `androidAppId` into the app module's own
      manifest with `tools:replace="android:value"` (confirmed present in a
      `npx expo prebuild --clean -p android` run), which by standard Android
      manifest-merger precedence should win over the library's empty value —
      but `expo prebuild` only generates the app module's manifest; it does not
      invoke autolinking or Gradle's manifest merger, so this has never actually
      been verified end-to-end. If it resolves empty, AdMob silently fails to
      initialize in the release build.

## Before tagging the release

- [ ] `changelogs/1.2.0.en.txt` and `changelogs/1.2.0.fa.txt` exist and
      read correctly (the Android release workflow fails the submit step
      otherwise).
- [ ] `app.json` `expo.version` bumped to `1.2.0` and
      `expo.android.versionCode` incremented, in the same commit as the
      `v1.2.0` tag (per the workflow's versioning contract).
- [ ] **Replace the placeholder AdMob _app_ ids in `app.json`.** The
      `react-native-google-mobile-ads` plugin block currently ships
      `"androidAppId": "ca-app-pub-XXXXXXXXXXXXXXXX~XXXXXXXXXX"` and the
      same value for `"iosAppId"`. Swap both for the real app ids from
      the AdMob console (AdMob → Apps → App settings → App ID).

      These are **not** the ad *unit* ids covered below: the app id
      (`~`-separated) identifies the whole app to the Mobile Ads SDK, the
      unit id (`/`-separated) identifies one ad placement. Both must be
      real, and they live in different files — app ids in `app.json`,
      unit ids in `.env`.

      This one is launch-critical rather than merely wrong: the Mobile
      Ads SDK reads the app id at process start, before any feature flag
      is consulted, and a malformed id is a documented hard crash on
      launch — for every user, even with `AD_REWARDS_ENABLED=0`. The
      `guard` job in `.github/workflows/android-release.yml` fails the
      build if the `ca-app-pub-XXXX` placeholder is still present, so a
      tag push cannot ship it, but fix it here rather than discovering it
      as a red build.
- [ ] Production ad unit ids swapped in for the AdMob test ids in `.env`,
      per the plan's launch checklist.
- [ ] `AD_REWARDS_ENABLED=1` is already live on the server **before** this
      build (carrying production ad unit ids) reaches users — see the
      ordering note below.

## Ordering: server flag before production ad units

Set `AD_REWARDS_ENABLED=1` and deploy `ad-reward` *before* shipping a build
that carries production ad unit ids — never after.

In the reverse order there is a live window where a user watches a complete
rewarded ad, the client polls for the grant, the server flag is still off so
no grant can ever arrive, the poll times out after ~8s, and the user is left
with "your credit is on its way" forever, having watched a real ad for
nothing. Test ad unit ids in a shipped build are harmless by comparison, so
the safe order is: flag on first, production units second.

The same ordering applies to the plan document's launch checklist
(`docs/superpowers/plans/2026-08-01-ads-for-ai-credits.md`); the two are kept
in sync deliberately.

## The signup grant is not behind the feature flag

`AD_REWARDS_ENABLED=0` stops ad-watch grants immediately, but it does **not**
affect the 5-credit signup grant. That grant lives in the Postgres trigger
function `tally_handle_new_user_profile`
(`supabase/migrations/20260801000000_ai_credits.sql`) and is unconditional —
a trigger cannot read an Edge Function env var, so this is by design, not an
oversight.

Practical consequence: turning ads off after launch does **not** reduce the
per-new-signup credit cost. Reverting or changing the signup grant requires a
separate migration, not a flag flip.

## Before applying the migration to production

The migration is applied by hand through the Supabase dashboard SQL editor.
Run these two queries **first**, in the same SQL editor, and read the output
before pasting the migration:

```sql
-- 1. Confirm what's currently live before this migration replaces it.
--    The migration does `create or replace function
--    public.tally_handle_new_user_profile()`, which silently overwrites
--    whatever is there. If prod's copy ever diverged from the original
--    migration's version (a hotfix applied straight in the dashboard, say),
--    this is the only chance to notice before that change is gone.
select prosrc from pg_proc where proname = 'tally_handle_new_user_profile';

-- 2. Confirm the trigger this migration assumes already exists still does.
--    The migration replaces the FUNCTION but never re-creates the TRIGGER,
--    so if the `auth.users` binding is missing the new function is dead
--    code and signup grants silently never fire — with no error anywhere.
select tgname from pg_trigger where tgrelid = 'auth.users'::regclass;
```

Query 1 should return the current function body (diff it against the version
in git). Query 2 must list the `auth.users` trigger that calls
`tally_handle_new_user_profile`; if it does not, create the trigger as part
of this deploy.
